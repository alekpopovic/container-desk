# Backend operation policy

Rust owns the operation registry and per-session policy. New backend-owned sessions always register with read-only access, independently of a saved host preference. Session registration binds host ID, renderer selection generation, session ID/generation and daemon identity. Re-registering a host resets its grants and intents. Removing a session also validates the full scope, so cleanup for an old generation cannot remove its replacement. Up to three active host policies are retained.

The registry currently allows typed plans for container list, inspect, bounded log snapshots, start/stop/restart and a container terminal using the fixed /bin/sh or /bin/bash choices. It has no arbitrary executable, script, Docker operation string, prune, remove, Compose deployment or user-selected flags. Additional product operations require their own later validated variants. Plans are argv only and cannot execute themselves. Remote POSIX quoting/context application is still a separate required increment before any plan reaches SSH.

Read operations remain allowed in read-only mode. Mutations require Manage or ManageAndTerminal; a terminal requires ManageAndTerminal. These checks run in Rust handlers, independently of disabled UI controls. Only a future explicit host-management opt-in handler may change runtime access. There is no renderer command to grant access in 007, and stored readOnly=false is never restored as an automatic grant.

Limits: full 64-character lowercase Docker IDs; 1–20 distinct explicit mutation targets; stop/restart grace period 1–120 seconds; log tail 0–20,000 and snapshot deadline 1–30 seconds; terminal columns 20–500 and rows 5–300. Unknown enum operations/shells and extra fields fail deserialization. Correctly shaped invalid IDs and numeric ranges return typed AppError. Registry result kinds map to explicit container list/detail/log snapshot, mutation outcome and terminal session DTOs. Handlers still return feature_unavailable after authorization because their remote transports do not yet exist.

Confirmation intents use 128 bits of OS randomness, a 30-second monotonic expiry and a maximum of 32 pending intents per session. Each intent binds the complete current scope, operation category/variant, exact ordered target IDs and numeric parameters. There is no intent persistence or automatic retry. Consumption removes the intent before returning an owned non-Clone authorization, including when operation parameters mismatch; repeated use fails. Expired intents fail, and changing access or replacing the session/daemon clears all intents. Different hosts cannot consume each other's intents.

Future transport integration must consume authorization under the session owner immediately before dispatch. If any await/queue occurs before spawning, revalidate the current scope/access at dispatch. Never reconstruct or replay a consumed mutation/terminal authorization after a timeout or reconnect. A lost dispatched response is an unknown outcome and must be reconciled with a read.

The local main-window capability permits the new inspect/log read handlers. Prepare/mutation/terminal handlers are registered for direct backend verification but deliberately have no granted window capability while unavailable; later feature prompts must explicitly add grants. Mock-runtime tests bypass that outer capability gate and still receive permission_denied from the Rust policy. No process launcher exists on these operation paths in 007; only the independent local SSH -V diagnostic from 006 can spawn a process.

Docker option verification used the installed CLI help without contacting a daemon and the official [stop](https://docs.docker.com/reference/cli/docker/container/stop/) / [restart](https://docs.docker.com/reference/cli/docker/container/restart/) references. The registry uses the supported `-t` timeout option. No Docker mutation or SSH host connection was run.

The ts-rs generator reports that it ignores serde's deny_unknown_fields attribute on the tagged confirmation enum. This is a validation-only attribute, not a wire-name transformation: serde still rejects unknown fields, explicitly verified in tests, and Rust/TypeScript tagged JSON fixtures match. The diagnostic is not suppressed. See [007 evidence](../codex/tracking/evidence/007.md).
