# Container lifecycle controls

Select a connected host and an existing container, then explicitly enable management for that session. New/reconnected sessions start read-only. The permission is held by Rust, is never restored from preferences and does not include terminal access. The control reads the backend permission when returning to a container. Saved hosts are labelled read-only by default; connection status describes the SSH session without making a stale permission claim.

Start, stop and restart prepare a new short-lived confirmation showing host name, actual daemon ID, container name/full ID, action and timeout. The backend obtains a current native inventory before issuing the intent and rejects absent IDs. The dispatcher checks a narrow current container-state projection and daemon/context binding again before sending. Individual actions are complemented by the explicit [batch and stopped-removal workflow](batch-actions.md).

Stop/restart accept integer timeouts from 1 to 120 seconds. Docker sends the configured stop signal and can kill the container after that grace period. Start uses no attach/interactive flags. Command deadlines are 30 seconds for start and timeout plus 10 seconds for stop/restart (maximum 130); snapshot deadlines remain 30 seconds. See Docker's official [start](https://docs.docker.com/reference/cli/docker/container/start/), [stop](https://docs.docker.com/reference/cli/docker/container/stop/) and [restart](https://docs.docker.com/reference/cli/docker/container/restart/) semantics, checked during 032.

Confirmation preparation waits up to three seconds for the existing host/global read admission before issuing its one inventory read. It never retries a dispatched operation. A submitted mutation owns its consumed intent/host lock and waits up to three seconds for one global command slot. A detached backend task holds both until preflight/command completion and child reaping, even if the original IPC waiter disappears. The current policy/session is rechecked after the bounded preflight. Remote arguments use the existing fixed builder, pinned daemon binding and central POSIX quoting; local OpenSSH is spawned directly.

Immediately before handing its one-use command to transport, the activity owner records Unknown durably. Native SSH exit 255, timeout, cancellation, signals, output overflow or transport failure remain Unknown; the command is never retried. Other nonzero exits mean command failure, not proof that remote state stayed unchanged. A successful exit reports command completion, not application readiness. Raw stdout/stderr are bounded at 64 KiB each and discarded rather than added to activity history.

After a completed/failed command the UI requests fresh inventory and inspect. It shows observed state and health, explicitly reporting pending convergence or a still-starting health check. If verification fails or the outcome is unknown, actions remain gated behind an explicit read refresh before another confirmation. Unknown history is retained across reconnect/app restart and shown for the selected host/container; a read refresh does not rewrite that historical uncertainty.

The lifecycle IPC methods bypass the finite-read retry scheduler. Late results cannot populate a different scope/container view. Both backend one-use intent/host locking and immediate UI admission prevent repeated clicks from dispatching another mutation. Turning management off clears pending intents. Any future terminal access still needs its own opt-in and capability.
