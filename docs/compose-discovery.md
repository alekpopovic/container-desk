# Compose discovery and read views

Compose projects share the selected host's existing native SSH session and verified Docker binding. Opening the Compose route performs a scheduled read; it never opens a second connection. Selecting an instance returns to the existing Containers detail/log view, using its full ID in the current inventory scope. Unavailable/stale container rows require a refresh before navigation.

When the remote Compose plugin is available, the backend runs the fixed `docker compose ls --all --format json` read. It parses project names, reported state and ConfigFiles metadata. Missing or unknown plugin availability still permits label grouping. A failed/malformed optional Compose listing is visibly identified while the label-based groups remain available; cancellation, identity drift and resource failures are not concealed as an empty list.

A fixed `docker ps --all --quiet --no-trunc --filter label=com.docker.compose.project` discovers IDs. The backend validates them and issues inspect projections in batches of at most 64. The fixed Go template contains only ID, name, state, project/service labels and reported config-file/working-directory labels. It does not emit environment values, other labels, health output or raw inspect JSON. Only the selected container's normal detail inspect runs separately; table rows do not create individual SSH processes. The normal inspect projection now also includes project/service grouping from exact labels.

Project and service identity is `(scope, project name, service, full container ID)`; identical service names in different projects never merge. Plugin data and inspected labels have separate provenance flags. Reported config-file values remain opaque strings, including comma-separated text or `N/A`; they are not assumed to form a complete or unambiguous file list. Every project configuration has status `unverified`. No reported path is read locally, checked remotely, opened as a URL or used to run Compose actions. Executable project configuration is a later, separate verification workflow.

Bounds are 1000 projects, 5000 instances, 128 distinct path/directory reports per project, 4096 bytes per field, 32 KiB per inspect projection record, 4 MiB per captured command and 16 MiB aggregate metadata, under a 30-second whole-read deadline. IDs are unique and batch responses must match the requested IDs exactly. A container disappearing during discovery fails that read and preserves stale UI data; the finite-read scheduler may retry the transient read within its existing limit. Daemon identity is verified before/after and session scope is fenced before publication.

The UI keeps last-success time and stale/error state, searches project names and pages both project choices and service instances in groups of 50. Text stays plain. Demo grouping uses only the existing synthetic container labels and never invokes SSH.

[Docker's Compose ls documentation](https://docs.docker.com/reference/cli/docker/compose/ls/) specifies `--all` and JSON output. [Compose's project-list implementation](https://github.com/docker/compose/blob/main/pkg/compose/ls.go) shows that ConfigFiles is derived from container labels and may be absent; reported metadata does not establish filesystem access or deployment readiness. Verification is recorded in `codex/tracking/evidence/029.md`, with isolated real Engine/Compose and plugin-absent tests separated from browser fixtures.
