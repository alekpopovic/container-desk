## Acceptance criteria

- Duplicate names/stable identity: two direct/jump records share a display name but receive distinct IDs; native reopen preserves the surviving ID. The renderer keys cards by ID, rejects foreign-host target/options and duplicate IDs, and never matches sessions by display name.
- Demo add/connect/disconnect/remove: Rust demo and browser UI run the entire sequence. Direct versus jump summaries, favorite/group filtering, comma-separated untrusted labels and local removal work. Demo operations leave live settings unchanged; delayed demo-mode writes after a mode switch are rejected.
- Live adapter: the production Backend and file store add direct-known/via-known records using explicit disposable config and real SSH/CLI. Both reach capability-ready against the synthetic API, display the correct effective route, disconnect with cleanup and reject old tokens. Removing the jump record leaves SSH config bytes unchanged; reopen retains only the direct record and opens no connection.
- Metadata editing: changing a favorite retains ID/token; changing alias/config/Docker target preserves the HostId while invalidating and cleaning the previous session. The UI retains the saved SSH default/explicit policy when editing metadata.
- Error/retry behavior: browser live bridge simulates resolution error, retains host/alias, shows relevant static diagnostics and dispatches another connect only on explicit Retry. This is UI evidence, not a live failure claim; native auth/permission failure paths remain independently verified in the lab.
- Removal semantics/read-only: native remove stops only the chosen owned session and writes metadata under expected revision; stale removal is rejected. No remote deletion or SSH-file write exists in the handler. New records/session workflow are read-only; older management preferences are not execution grants.
